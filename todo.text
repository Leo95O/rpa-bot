# AI_CONTEXT.md — Contexto técnico del proyecto RPA E2E (logisticaview)

> Manual de instrucciones **IA a IA**. Léelo completo antes de tocar código.
> El objetivo de este repo es ejecutar pruebas E2E que automatizan un flujo transaccional
> (crear insumos → compras → guías de ingreso → validaciones de Kardex) contra una aplicación
> legacy **AngularJS v1.x** con backend **PHP/MySQL**.

---

## 1. Stack tecnológico

| Capa | Tecnología | Notas |
|------|------------|-------|
| Automatización | **Playwright** (`chromium.connectOverCDP`) | Se conecta a un Chrome ya abierto vía CDP, **no** lanza navegador propio. |
| Runtime | **Node.js + ts-node** | Scripts ejecutados con `ts-node src/*.ts`. Compilado con `tsc` a `dist/`. |
| Excel | **exceljs** | Lectura del Excel de datos (`parser.ts`) y escritura del reporte (`test-e2e.ts`). |
| BD | **mysql2** (promise) | Limpieza de base de datos en `db.ts`. |

Dependencias (package.json): `playwright`, `exceljs`, `mysql2` + devDeps `ts-node`, `typescript`, `@types/node`.

Scripts npm:
- `npm run test:e2e` → `ts-node src/test-e2e.ts` (orquestador E2E actual).
- `npm run build` → `tsc -p tsconfig.json`.
- `npm start` → `node dist/index.js` (orquestador legacy por Excel).
- `npm run dev` → `ts-node src/index.ts` (orquestador legacy por Excel).

## 2. Peculiaridades del FRONTEND (CRÍTICO — AngularJS legacy)

### 2.1. Qué es la app
- SPA AngularJS **v1.x** servida en `http://localhost:9002` (estado UI-Router vía hash, ej. `#!/escritorio`).
- Backend API REST en `http://localhost:9001`, con el módulo logística en el prefijo
  `BACKEND_LOGISTICA` = `/restaurant/logistica/rest/` (definido en `logisticaview/app/scripts/definitions.js`).
- Código fuente frontend: `C:\Practicas\RESTAURANT_PROYECT\logisticaview`.
- Código fuente backend: `C:\xampp\htdocs\webapp` (logística en `\logistica`).

### 2.2. Cómo extraer/inyectar datos en el `$scope`
Toda interacción se hace con `page.evaluate()` dentro del contexto del navegador. El patrón base:

```ts
await page.evaluate(async () => {
  const injector = angular.element(document.body).injector();
  const $rootScope = injector.get('$rootScope');          // raíz de scopes
  const CommonCollection = injector.get('CommonCollection'); // búsquedas/catálogos
  const Insumo = injector.get('Insumo');                  // modelo/factory de insumos
  const Compra = injector.get('Compra');                  // modelo/factory de compras
  const Guia   = injector.get('Guia');                    // modelo/factory de guías
  const SecurityService = injector.get('SecurityService'); // local/usuario/token actual
  const PARAM = injector.get('PARAM');                    // constantes SI/NO/ACTIVO/TODOS
  // ... lógica ...
});
```

### 2.3. Encontrar el controlador (`vm`) de una vista (scope-walk)
Cada vista usa `controllerAs: 'vm'`. Para llegar al `vm` correcto se recorre el árbol de scopes
desde `$rootScope` buscando una **marca distintiva** (una función/propiedad única del controlador):

```ts
function encontrarScope(marca) {
  let found = null;
  (function walk(s) {
    if (found) return;
    if (s.vm && marca(s.vm)) { found = s; return; }
    let c = s.$$childHead;
    while (c) { walk(c); c = c.$$nextSibling; }
  })($rootScope);
  return found;
}
```

Marcas útiles (funciones del `vm`):

| Estado UI-Router | Marca (`s.vm.X`) | Módulo que lo usa |
|---|---|---|
| `logistica.insumos.nuevo` | `typeof s.vm.registrarInsumo === 'function'` | `bot.ts` (crear insumo) |
| `logistica.compra.nuevacompra` | `typeof s.vm.procesarDatosCompra === 'function'` | `bot.ts` (registrar compra) |
| `logistica.compra.editarcompra` | `typeof s.vm.fnActualizarCompra === 'function'` | `compras.ts` (modificar) |
| `logistica.guiacompra.nuevaguia` | `s.vm.guia && typeof s.vm.guia.agregar === 'function'` | `guias.ts` (registrar guía) |
| `logistica.guiacompra.editarguia` | `s.vm.guia && typeof s.vm.fnobtenerGuia === 'function'` | `guias.ts` (modificar guía) |
| `logistica.kardex.individual` | `typeof s.vm.fnPrepararFiltrosParaCargarKardex === 'function'` | `kardex.ts` (legacy) |

### 2.4. Navegación
```ts
// bot.ts
export async function navegar(page, estado, params?) {
  await page.evaluate((a) => {
    const injector = angular.element(document.body).injector();
    injector.get('$state').go(a.estado, a.params);
  }, { estado, params });
}
```
Estados: `logistica.escritorio`, `logistica.insumos.nuevo`, `logistica.compra.nuevacompra`,
`logistica.compra.editarcompra` (param `{ idCompra }`), `logistica.guiacompra.nuevaguia`,
`logistica.guiacompra.editarguia` (param `{ idGuia }`), `logistica.kardex.individual`.

### 2.5. Ciclo `$digest` y esperas (la fuente nº1 de bugs)
AngularJS actualiza el modelo en un `$digest` **asíncrono**. Después de una respuesta HTTP el
`.then()` que puebla `vm.X` corre recién en el siguiente digest. Por eso:
- Tras disparar una acción, usa `esperarEndpoint(page, urlPart, timeout)` (basado en
  `page.waitForResponse`) para esperar la respuesta de red.
- Luego usa `page.waitForFunction(...)` para esperar a que el **modelo** ya esté poblado
  (p. ej. `s.vm.compraList.length > 0 && s.vm.showLoading === false`).
- `page.waitForTimeout(ms)` para asentar la UI (modals, re-renders).

### 2.6. Grillas HandsOnTable (y su trampa)
Las tablas de detalle usan la directiva `rp-hot` (HandsOnTable). El `ng-model` es el array en el
`vm`:
- Compras: `vm.compra.detallecompraList` (y `vm.compra.detallecompraListParaBackend` tras `procesarDatosCompra`).
- Guías: `vm.guia.detalleguiaList`.
- Kardex: `vm.compraList` (grid `id="hot-kardexList"`, **no** existe `.kardex-grid`).

> **Trampa comprobada:** leer el stock/costo desde la grid del Kardex (`vm.compraList`) devolvía
> `stock=0`/`costo=0` de forma no fiable (problemas de filtro de almacén + digest + formato).
> **Solución adoptada:** leer el stock/costo vía el endpoint autoritativo `Insumo.obtenerStockYCosto`
> (ver §3.3), no desde el `$scope` de la grid.

### 2.7. Modales residuales (SweetAlert2 / rpAlert)
Tras registrar insumos/compras, la app muestra un SweetAlert2 ("Guardado exitoso"). Un modal
residual **bloquea la siguiente navegación** (timeout en `waitForFunction`). Mitigación en `bot.ts`:

```ts
export async function cerrarModales(page) {
  try { const c = await page.$('.swal2-confirm'); if (c) await c.click(); } catch {}
  try { const c = await page.$('.swal2-close');   if (c) await c.click(); } catch {}
  await page.waitForTimeout(300);
}
```
`crearInsumo` la llama **antes y después** de registrar cada insumo.

### 2.8. Botones por CSS vs funciones del controlador
Para guardar guías (edición) resultó más fiable **hacer click por CSS** que llamar a la función del
`vm` (que podía no estar expuesta o pedir confirmación). Flujo en `guias.ts`:

1. `button[ng-click="vm.procesarDatosGuia()"]` (Continuar) → muestra previsualización.
2. `button[ng-click="vm.fnActualizarGuia()"]` (Editar guía) → dispara `actualizarGuia`.
3. `.swal2-confirm` → confirma el diálogo de confirmación.

## 3. Peculiaridades del BACKEND y BD

### 3.1. Backend PHP (Slim 3) + MySQL
- Base de datos: **`logistica`** en `localhost`, usuario `root` sin password (acceso por CLI con
  `C:\xampp\mysql\bin\mysql.exe -u root logistica`).
- Respuestas envueltas: `{ tipo, mensajes: [], data }`.
  **`tipo` es string**: `SUCCESS='1'`, `ERROR='3'`, `DANGER='3'`. Siempre comparar con
  `Number(tipo) === 1`, nunca `=== 1`.

### 3.2. `db.ts` — limpieza con `FOREIGN_KEY_CHECKS = 0`
`limpiarBaseDatos()` borra (en orden) `presentacioninsumo`, `movimientoalmaceninsumo`,
`almacenproductoinsumo` e `insumo`, envuelto en:

```sql
SET FOREIGN_KEY_CHECKS = 0;   -- antes
... DELETE FROM ... ;
SET FOREIGN_KEY_CHECKS = 1;   -- después
```

Motivo: `insumo` es referenciado por ~40 tablas (`insumoequivalencia`,
`impuestocompraproductogeneralinsumo`, etc.). Sin desactivar FKs, `DELETE FROM insumo` revienta.

> **OJO:** la limpieza **NO borra** `compra`, `detallecompra`, `guia`, `detalleguia`,
> `notacreditocompra`. Por eso los comprobantes (serie/número) se hacen únicos con `Date.now()`
> (ver §3.4) para no chocar con corridas anteriores.

### 3.3. Lectura de stock/costo — `Insumo.obtenerStockYCosto`
Endpoint `GET producto/insumo/obtenerStockYCosto/{insumo_id}` → `data[]` con un elemento por
almacén con control de stock. Campos relevantes:

```json
{
  "almacen_id": 1,
  "almacen_descripcion": "Almacen Principal",
  "stock": 10,
  "costo": 2.0,
  "costoStock": { "costo": 2.0, "stock": 10, "costopromedio": 0, "costosinimpuesto": 1.695 }
}
```

> **Clave:** `costoStock.costopromedio` suele ser **0** porque el backend (`InsumoLogistica::getStockCosto`)
> solo lo calcula si recibe el flag `retornar_costo_promedio`, que `obtenerStockYCosto` **no** envía.
> **Leer siempre `data[].costo`** (el costo promedio real, con impuestos). `kardex.ts` usa `costo`
> como primario y `costoStock.costopromedio` solo como fallback si es `> 0`.

### 3.4. Comprobantes únicos con `Date.now()`
`compras.ts` (`registrarCompra`) y `guias.ts` (`registrarGuia`) añaden un sufijo temporal al
número para evitar colisiones de serie/número (que el backend valida con
`CompraLogisticaValidator::existeCompra()`):

```ts
numero: p.numero + '-' + Date.now()            // compras
guia_numeroguia = args.numero + '-' + Date.now()  // guías
```

### 3.5. Otros datos de backend aprendidos
- **Proveedor**: se busca con `CommonCollection.obtenerProveedorPorBusqueda(nombre)`. Devuelve
  objetos con `proveedor_id`, `proveedor_razonsocial`, `proveedor_ruc`. El `proveedor_id` válido se
  captura **directo de la respuesta de búsqueda** (no de `vm.compra.proveedorSeleccionado`, que
  Angular puede resetear).
- **Fecha de compra** debe ir formateada `YYYY-MM-DD HH:mm:ss` (`moment(...).format(...)`). Un string
  `YYYY-MM-DD` suelto es rechazado ("La fecha de la compra no es valida").
- **Búsqueda de items**: `CommonCollection.busquedaSensitivaSegunTipos(...)` con 21 argumentos
  posicionales (ver firma en `collection.common.js`). Devuelve `data[]` con `item_id`, `item_tipo`
  (`1`=insumo, `2`=producto), `item_descripcion`, `item_codigo`.
- **Config que desactivaría el stock síncrono**: `CONFIGURACION_ENTRADAS_SALIDA_STOCK_DESDE_MODULO_CONTROL_STOCK`
  (id `38`) está en `0` para el local 1 → **el stock SÍ se actualiza sincrónicamente** (no hay worker
  fire-and-forget activo). Si un día el Kardex "no aparece", verificar esta config antes de asumir
  un problema asíncrono.
- **Config costo sin impuestos**: `CONFIGURACION_MOSTRAR_COSTO_SIN_IMPUESTOS` (id `72`) en `0` →
  `costo` incluye impuestos.
- **Presentación en compras (CRÍTICO)**: la búsqueda `busquedaSensitivaSegunTipos`
  (`InsumoLogistica::parseBusquedaSensitiva`) devuelve `item_presentacionid` / `item_presentacion`
  (la presentación **por defecto**), **NO** `presentacionList`. Si `resolverItem` de `bot.ts` lee
  `presentacionList` y no cae a `item_presentacionid`, `presentacioninsumo_id` termina `NULL` en
  `detallecompra`. Consecuencias encadenadas: (1) el backend **no incrementa stock** (Compra
  Fantasma) y (2) `obtenerDetallesCompra` **no expone `item_id`/`item_descripcion`** (los items del
  dump salen `{}` → Buscador Ciego). Para una presentación concreta por nombre ("Caja de 24") hay
  que consultar `Insumo.obtenerInsumoDetallado(insumo_id,0,0)` → `data.listaPresentaciones`
  (`presentacioninsumo_id`, `presentacioninsumo_nombre`, `presentacioninsumo_cantidad`).

1. `test-e2e.ts` → `limpiarBaseDatos()` (db.ts) → `conectarNavegador()` (bot.ts) → `navegar('logistica.escritorio')`.

3. `validarStock(nombre, stock, costo)` (kardex.ts) → `Insumo.obtenerStockYCosto`.
4. `registrarCompra/modificarCompra/anularCompra/registrarNotaCredito` (compras.ts) usando `insumoId`.
5. `registrarGuia/modificarGuia/anularGuia` (guias.ts) usando `insumoId`.
6. `generarReporte(reporte)` → `data/Reporte_Bot.xlsx`.


Debe ser un Chrome **dedicado** (sin sesiones abiertas) porque `connectOverCDP` se conecta al
puerto `9222` y el bot reutiliza la pestaña ya abierta y logueada en la app (`localhost:9002`).

Flujo: limpia BD → conecta a Chrome → navega a `escritorio` → Fase 1/2/3 → escribe

## 6. Aprendizajes duros (resumen de errores resueltos — no repetirlos)

1. **`localhost` vs `127.0.0.1`**: `connectOverCDP('http://localhost:9222')` falla por IPv6 (`::1`).
   Usar `http://127.0.0.1:9222`.
2. **`tipo` de respuesta es string**: comparar `Number(tipo) === 1`.
3. **`proveedor_id`**: capturar del resultado de búsqueda, no de `vm.compra.proveedorSeleccionado`.
4. **Fecha de compra**: `YYYY-MM-DD HH:mm:ss`.
5. **`compra_fecha` se anula tras `procesarDatosCompra`**: capturar `proveedor_id`/`moneda_id`/
   `local_id`/`almacen_id` **antes** de `procesarDatosCompra`.
6. **Esperar el `$digest`**: tras cada respuesta HTTP, esperar a que `vm.X` esté poblado.
7. **Modales residuales**: `cerrarModales()` antes/después de cada acción.
8. **No leer stock/costo del `$scope` de HandsOnTable**: usar `Insumo.obtenerStockYCosto` y `data[].costo`.
9. **Colisión de serie/número entre corridas**: sufijo `Date.now()`.
10. **Localización de items por `insumo_id`** (estricto), no por texto.
11. **Guías: guardar por click CSS** (Continuar → Editar guía → `.swal2-confirm`), no por `vm.fnActualizarGuia()`.
12. **No existe worker asíncrono de stock** (config 38 = 0): el Kardex es síncrono.

## 0. Recetas Playwright transversales (aplican a todos los flujos futuros)

### 0.1 Ciclo `$digest` — estrategia estable tras mutar `$scope` vía `page.evaluate`

Hallazgo: el módulo **no usa `$scope.$apply()` en ningún punto**; todo corre dentro de `$timeout` (digest seguro) o callbacks de HandsOnTable. Los recálculos están enganchados así:

- `$scope.$watch("vm.porcionamientoDeRecetas.insumos", …, true)` y `…presentaciones` (`porcionarReceta.controller.js:2048-2049`), más `_calcularCostoTotalDeLaPreparacion` con debounce `$timeout 100ms` (`:2023`).
- Edición de grilla vía `Handsontable.afterChange` (wrapper `HandsontableService.addEventAfterChange`, ignora `source==="setEmpty"`).

Estrategia recomendada (en este orden, de menos a más frágil):

1. **Preferir `$timeout` sobre `$apply`**: envolver la mutación en `injector.get('$timeout')(fn)` o simplemente mutar y esperar 300ms. `$apply` dentro de un digest en curso lanza `"$digest already in progress"`; `$timeout` lo encola de forma segura.
2. **Disparar el `afterChange` real en vez de mutar el array a pelo**: usar `hot.setDataAtCell(fila, col, valor)` sobre la instancia (`vm.onLoadHotRecetas(instance)` / `vm.onLoadHotPresentaciones(instance)` guardan la instancia). Esto ejecuta la cadena de recálculo (`hotRecetasCantidadAPrepararAfterChange:881`, `hotPresentacionesCantidadResultanteAfterChange:2876`) exactamente como un usuario.
3. Si se muta el array directamente (más rápido para N filas): llamar después al recalculador explícito que corresponda (`vm.recalcularTotalesPorcionable()`, `recalcularValorizadoResultantesPorCantidades(receta)`) dentro de `$timeout`, y luego `hot.render()`.
4. Barrera de espera: `page.waitForFunction` sobre el **pie calculado** (ej. `vm.porcionamientoDeRecetas.recetaSeleccionada.item_cantidadResultante === X`), no `waitForTimeout` fijo.

```ts
// Patrón digest-seguro
await page.evaluate(() => {
  const inj = angular.element(document.body).injector();
  const $timeout = inj.get('$timeout');
  // ... localizar scope/vm ...
  $timeout(() => { vm.recalcularTotalesPorcionable(); });
});
await page.waitForFunction((esp) => {
  // walk hasta vm.porcionamientoDeRecetas.recetaSeleccionada y comparar resultante
}, esperado, { timeout: 15000 });
```

Fuente: `api/entity/Preparacionreceta.php:523-776, 862-926`. Orden: `disminuirStockPorcionable()` → `obtenerCostoPorUnidadProducida()` → `obtenerCostoFactor()` → loop `incrementarStockPorCompra(ENTRADA_PORCIONAMIENTO, …)`.

### 4.1 Prorrateo — TODOS los destinos reciben el MISMO costo unitario

```php

$cantidad_restar_stock = conversionUM(origen_UMmin, $resultado, destino_UM);
```

Comentario literal del autor (`:871-892`): `1k+0.5k=(2k*8)=16; 1.5K=16; 1k=10.66` → `DP1(1k)=10.66, DP2(0.5k)=5.33`. Cada destino: `valorizado = cantidad_destino × costoFactor` (`:648-660`). **No es ponderado por peso, ni partes iguales, ni % manual** — el % solo aplica si está activa `CONFIGURACION_ALTERAR_COSTO_VALIDAR_CANTIDAD_PORCIONAR_INSUMO_LOGISTICA` y viene `presentacionresultantereceta_valorizado` (`:638-640`).

Ejemplo oráculo (Pollo 10kg @ S/8/kg = S/80 → Pechuga 6kg + Alitas 3kg, merma 1kg ON): `resultado=9`, `costoFactor = 8×9/9 = 8` → Pechuga `6×8=48`, Alitas `3×8=24`, merma `1×8=8` aparte. Suma `48+24+8=80` ✓.

### 4.2 Merma — NO encarece las piezas (al contrario de la intuición)

`PreparacionrecetaLogisticaController:973-986`: si `generarMerma=='1'` **y** `merma>0` → `resultado = APreparar − merma`. Registro (`:523-536, 778-856`): fila `merma` (`razon="Merma por porcionamiento de insumo: X"`, `importe = costoAprox_origen × merma`) + `detallemerma(costo, cantidad, importe)` + Kardex `SALIDA_MERMA_PORCIONAMIENTO` (motivo 15) con `merma_id` como `idmotivo`.

Consecuencia para el oráculo: como `costoFactor` divide entre el `resultado` **neto**, cada kilo útil conserva el costo unitario del origen — la merma se valoriza por separado y sale por su propio movimiento. `cantidadDescargarStockInsumoPorcionado = resultado + merma` se calcula pero **no entra al divisor**.

# **Manual Maestro de Arquitectura y Operación Logística (ERP)**

# **1\. Arquitectura del Sistema y Flujo Transaccional**

El sistema ERP opera bajo una arquitectura de Cliente Rico (Frontend) acoplado a una API RESTful (Backend) mediante un modelo MVC extendido con un enfoque de Fat Model (Modelo Gordo). El objetivo central es separar estrictamente el enrutamiento HTTP de las reglas de negocio y del acceso a la base de datos, comunicando ambas capas exclusivamente mediante un contrato JSON estandarizado ({tipo, mensajes, data}).

## **1.1. Capas del Frontend (Cliente \- AngularJS)**

El cliente gestiona el estado y la validación en tiempo real antes de tocar la red, ahorrando ancho de banda y mejorando la UX.

* Template (\*.html): Interfaz de usuario (UI), renderizado condicional y captura de eventos.  
* Controller (\*.controller.js): Lógica de la vista, manejo de loaders (spinners) y estado de la interfaz.  
* Collection (collection.\*.js): Gestor de listas en memoria que transforma JSON plano en Modelos enriquecidos.  
* Resource (resource.\*.js): Mensajero de red que encapsula \$http y gestiona las promesas.  
* Model (\*.js): Instancias con comportamiento local y reglas visuales (ej. calcularTotal()).

## **1.2. Capas del Backend (Servidor \- PHP)**

El servidor procesa la lógica pesada y garantiza la integridad de los datos.

* Router (index.php): Micro-framework (Slim). Intercepta la petición HTTP y despacha al controlador. No sabe de reglas de negocio.  
* Controller (\*Controller.php): Orquesta la operación, instanciando clases y devolviendo el JSON estandarizado. No ejecuta SQL.  
* Validator (\*Validator.php): Filtro de seguridad (ej. validación de stock, fechas). No persiste nada.  
* Modelo de Dominio (\*.php): Núcleo del negocio. Afecta el Kardex y calcula montos. No escribe SQL directamente.  
* Entity / ORM (\*Entity.php): Data Access Layer. Única capa autorizada a ejecutar operaciones preparadas en MySQL, previniendo inyecciones SQL.

## **1.3. Ciclo de Vida de Guardado (End-to-End)**

1. Ida: El usuario hace clic en guardar en el Template. El Controller (JS) enciende el spinner y delega a la Collection, que valida y empaqueta los datos. El Resource envía el POST (JSON).  
2. Procesamiento: El Router recibe el payload y lo pasa al Controller (PHP). El Validator aplica reglas estrictas (si falla, retorna error y corta el flujo). Si aprueba, el Modelo ejecuta la matemática del Kardex y la Entity guarda en la Base de Datos.  
3. Vuelta: El Controller (PHP) retorna 200 OK SUCCESS. El Resource resuelve la promesa, la Collection instancia el nuevo objeto en memoria, y el Controller (JS) apaga el spinner, actualizando la vista para que el Template muestre la notificación de confirmación verde.  
   

### **1.4. Tipología de Ítems y su Comportamiento en el Kardex**

El sistema clasifica el inventario en tres grandes familias. Esta distinción es obligatoria porque define por qué módulos pueden transitar y cómo impactan la rentabilidad del negocio:

* **Insumos (Materia Prima):**  
  * **Definición:** Bienes físicos que sufren transformación. Son la base del *Food Cost*.  
  * **Comportamiento en Kardex:** Ingresan masivamente a través del módulo de **Compras**. Disminuyen a través de **Producción** (al preparar recetas base) o **Ventas** (por explosión de materiales al vender un plato).  
  * **Ejemplo:** Carne, arroz, verduras.  
* **Consumibles (Materiales Operativos y Empaques):**  
  * **Definición:** Bienes físicos que se agotan con el uso, pero no se comen ni se transforman químicamente. Impactan el costo operativo, no el costo de la receta teórica.  
  * **Comportamiento en Kardex:** Ingresan por **Compras**. Generalmente, se retiran del Kardex mediante el módulo de **Almacenes (Salida de Stock / Mermas)** justificándolos como gasto de operación, o se amarran como adicionales en las ventas de *delivery*.  
  * **Ejemplo:** Cajas de hamburguesa, servilletas, guantes, lejía.  
* **Productos (Bienes Finales / Terminados):**  
  * **Definición:** Ítems listos para ser entregados al cliente final. Tienen un precio de venta al público.  
  * **Comportamiento en Kardex:**  
    * *De fabricación interna:* Ingresan al Kardex exclusivamente a través del módulo de **Producción (Salida de Producción)** y salen a través de **Ventas**.  
    * *De reventa:* Ingresan al Kardex directamente por **Compras** (ej. bebidas embotelladas) y salen por **Ventas**.  
  * **Ejemplo:** Hamburguesa Royal (fabricación interna), Gaseosa 500ml (reventa).


# **2\. Módulo de Compras (Aprovisionamiento y Costos)**

El Módulo de Compras es el motor de abastecimiento y control financiero. Garantiza que cada gasto esté justificado documentalmente, que el Kardex se actualice con precisión y que el Food Cost se calcule sobre precios reales de mercado. Se rige por la estricta separación de bienes físicos (afectan inventario) y bienes intangibles (solo afectan finanzas).

## **2.1. Cadena de Documentos Físicos (El Kardex)**

* Solicitud de Compra: Documento interno de requerimiento sin precios pactados. Informa formalmente a logística qué insumos necesita un área y para cuándo.  
* Orden de Compra: Documento externo y comercial que confirma al proveedor la cantidad y el precio pactado. Proyecta el gasto y permite consolidar requerimientos de varias sucursales para mayor poder de negociación (gestión visible en la Distribución de Órdenes de Compra, una pantalla inmutable de auditoría).  
* Guía de Compra (Opcional): Documento de recepción física. Su registro suma inmediatamente el stock en el Kardex para que la cocina opere, separando el flujo físico del contable.  
* Compra (Obligatoria): Documento maestro (factura/boleta). Recalcula el precio promedio unitario, afecta las cuentas por pagar y deduce impuestos. Bloquea su guardado si carece de Proveedor o Serie/Número. Posee una dualidad de fechas (Fecha de compra vs. Fecha de tributación).  
* Nota de Crédito: Corrección contable estrictamente vinculada a una Compra original. Disminuye la deuda y, dependiendo del caso, ajusta el inventario por devoluciones, manteniendo exacto el Food Cost.

## **2.2. Gestión de Intangibles y Financiamiento**

* Compras Rápidas: Contingencias de caja chica. Exige descripción y precio, pero omite el Kardex. Genera una salida de caja inmediata.  
* Órdenes y Compras de Servicio: Flujo para bienes intangibles (mantenimiento, fumigación). La Orden estima el gasto y la Compra de Servicio registra la boleta oficial para obtener crédito fiscal, sin alterar el inventario de alimentos.  
* Compras por Pagar: Panel financiero (Accounts Payable) para facturas al crédito. Gestiona cuotas, intereses, amortizaciones y genera layouts bancarios (ej. BBVA NetCash) para pagos masivos.  
* Plantillas y Borradores: Herramientas de agilidad. Los borradores pausan el registro de facturas largas sin afectar la base de datos, y las plantillas autocompletan pedidos recurrentes.

# **3\. Módulo de Producción (Transformación y Trazabilidad)**

Funciona bajo una lógica MRP (Planificación de Requerimientos de Materiales). Ninguna preparación inicia sin justificar un requerimiento matemático contra el inventario.

## **3.1. Planificación (Workflow de 7 etapas)**

1. Requerimientos: Sugerencia matemática de demanda ((Ventas Proyectadas) \- (Stock Actual)).  
2. Órdenes de Producción: Mandato oficial de trabajo con explosión de materiales y valorización en tiempo real.  
3. Solicitudes de Compra: Freno de seguridad automático si se detecta déficit de insumos para la orden.  
4. Reparto Interno: Traslados desde el almacén principal al área de cocina.  
5. Producción: Ejecución y cocción.  
6. Salida de Producción: Liberación del producto terminado.  
7. Abastecimiento: Ingreso al almacén de venta.

## **3.2. Asientos de Transformación (El Motor del Kardex)**

La producción en el sistema opera como un asiento de doble vía, donde el valor financiero se hereda o prorratea, manteniendo el balance total del inventario:

* Preparar Recetas (Transformación Química): Ejecuta la explosión de materiales. Descuenta insumos crudos y da de alta productos cocinados (ej. salsas, masas), asignándoles la suma del costo de sus ingredientes y un Número de Lote para trazabilidad.  
* Porcionar Recetas (Transformación Física): Pasa un producto terminado a granel (Kilos/Litros) a formatos de venta (Unidades empacadas), prorrateando el costo financiero total entre las nuevas porciones.  
* Porcionar Insumos (Desposte): Toma una pieza entera (ej. Pollo entero) y la divide en cortes (Pechuga, Alitas). Distribuye matemáticamente el costo de la pieza entre los cortes resultantes. Posee un control de Merma, que absorbe financieramente el desperdicio operativo (huesos, grasa) para que los cortes útiles reflejen su costo real encarecido.

## **3.3. Trazabilidad y Prevención**

* Dashboard de Lotes: Monitorea la "salud" de los productos preparados, listando Lotes Activos, Por Vencer (Alerta) y Vencidos (Críticos).  
* Prevención de Duplicidad: El sistema restringe el descuento manual de insumos en cocina. Si una receta está configurada como "Stock en Almacén", se descuenta al usar el módulo Preparar. Si es "Preparación en Venta", se descuenta automáticamente por detrás al facturar en la caja (POS).

# **4\. Módulo de Almacenes (Distribución, Control y Conciliación)**

Núcleo transaccional de la logística física, encargado de blindar el sistema contra pérdidas y mermas ocultas.

## **4.1. Ejecución Logística y Traslados**

* Requerimiento de Stock: Pedido interno manual o generado de forma predictiva mediante el análisis de movimientos (consumo histórico x días a abastecer) o Just-In-Time (por pedidos delivery confirmados).  
* Orden de Movimiento: Aprobación e instrucción de preparación (picking/packing) en el origen.  
* Movimiento entre Almacenes: Ejecución del traslado. Descuenta stock del origen, suma al destino y arrastra el Costo UM Base, garantizando que el Food Cost viaje con la mercadería.  
* GRE (Guía de Remisión Electrónica): Emisión obligatoria del XML a SUNAT para el traslado físico por vía pública, controlando modalidades de transporte (Privado vs. Tercerizado) con validaciones inmutables (Placa, Licencia, Ubigeo).

## **4.2. Control, Conciliación y Ajustes**

* Arqueo de Inventario: Auditoría preventiva de rutina (diaria/por turno) enfocada en ítems críticos o de alto valor. Solo evalúa cantidades mayores a cero.  
* Cuadre de Stock: Conciliación correctiva masiva o segmentada. Puede ser estándar, "ciego" (oculta el stock teórico para forzar el conteo real) o mediante carga masiva (Excel). Calcula automáticamente el impacto monetario de la Sobrevalorización y la Pérdida.  
* Salidas y Reservas: Módulo para asentar bajas físicas por merma, consumo de personal o roturas (afectando cuentas de gasto), y para reservar virtualmente mercadería (Stock Físico vs. Stock Disponible) previniendo que se consuma por error.  
* Sincronización de Stock: Módulo de mantenimiento que recalcula el Kardex de forma retrospectiva cuando ocurren eventos asíncronos (ej. registrar una compra días después de haberse consumido el stock), reprocesando los costos promedio y eliminando saldos negativos históricos.

## **5\. Mapa de Flujos, Transiciones y Canjes**

El sistema no opera como módulos aislados, sino como un ecosistema donde los documentos se transforman (canjean) siguiendo rutas estrictas basadas en la naturaleza del ítem (Insumo, Consumible o Producto). A continuación, se detallan los caminos lógicos extraídos del diagrama de flujo arquitectónico.

### **5.1. El Nodo Central: Requerimiento de Stock**

El **Requerimiento de stock** actúa como el gran distribuidor logístico. Al generarse un requerimiento (ej. un local necesita mercadería), el sistema evalúa la disponibilidad y el tipo de ítem para desviar el flujo por tres caminos posibles:

* **Hacia Solicitud de Compra (Desvío Externo):** Si el ítem (Insumo o Consumible) no tiene stock en ningún almacén de la empresa, el flujo se envía a Compras para adquirirlo de un proveedor externo.  
* **Hacia Orden de Movimiento (Desvío Interno):** Si el ítem (Insumo, Consumible o Producto) tiene stock en el almacén central, el flujo se convierte en una orden para trasladarlo físicamente a la sucursal que lo pide.  
* **Hacia Proceso / Orden de Producción (Desvío de Transformación):** Si el ítem es un Producto de fabricación interna (ej. salsa base) que no está en stock, el flujo exige a la cocina central que lo fabrique.

### **5.2. Ruta de Aprovisionamiento (Bienes Físicos)**

Este es el camino lineal para adquirir bienes que afectarán la rentabilidad. Solo transitan por aquí Insumos, Consumibles y Productos de reventa.

* **Secuencia de Canje:** Solicitud de compra ➔ Orden de compra ➔ Guía de compra ➔ Compra ➔ Nota de crédito de compra.  
* **Impacto Escalonado:**  
  * La *Orden de compra* proyecta la salida de dinero.  
  * La *Guía de compra* suma las unidades físicas al Kardex.  
  * La *Compra* recalcula el Costo Promedio Unitario y asienta la cuenta por pagar.

### **5.3. Ruta Financiera Intangible (Servicios)**

Ruta aislada diseñada para gastos operativos que no se almacenan (ej. mantenimiento).

* **Secuencia de Canje:** Orden de servicio ➔ Compra de servicio.  
* **Regla de Negocio:** Ningún documento de este flujo toca el Kardex ni se cruza con las guías de recepción físicas. Afectan directamente las cuentas por pagar y el estado de resultados.

### **5.4. Ruta de Producción y Abastecimiento de Cocina**

Flujo complejo que interconecta la necesidad de fabricar con la logística de movimiento y compras. Aquí los Insumos se transforman en Productos.

* **Interacciones de la Orden de Producción:**  
  * ➔ **Hacia Solicitud de compra:** Si al explotar la receta faltan insumos crudos, la orden de producción exige comprar antes de cocinar.  
  * ➔ **Hacia Orden de movimiento:** Si los insumos existen pero están en otro almacén, dispara un traslado interno.  
* **Ejecución:** Una vez asegurados los insumos a través de los movimientos internos, se ejecuta la transformación, descontando la materia prima y dando de alta el Producto terminado en el Kardex.

### **5.5. Ruta de Logística Interna y Salidas**

Flujo para la redistribución y baja de mercadería sin fines de venta.

* **Secuencia de Traslado:** Orden de movimiento ➔ Movimiento interno.  
* **Documentación y Baja:** Movimiento interno ➔ Guía interna ➔ Salida.  
* **Regla de Negocio:** La *Guía interna* se utiliza para justificar traslados por vía pública (GRE). La *Salida* se usa como destino final para retirar Consumibles (uso operativo) o dar de baja Insumos/Productos mermados, sin generar ingresos económicos.

## Convención de capas (reglas arquitectónicas del módulo)

Logística **NO** usa `base/entitybase/entity` (a diferencia del núcleo `api/`). Sigue su propio stack:

| Capa | Ubicación | Convención de nombre | Responsabilidad |
|------|-----------|----------------------|-----------------|
| Rutas | `logistica/rest/{dominio}/index.php` | 1 archivo `index.php` por dominio (Slim 3) | Definir endpoints y handlers `($request, $response, $args)` |
| Controlador | `logistica/controllers/` | `{Entidad}LogisticaController` (monolítico) | Lógica de negocio; un controlador por entidad |

> **Nota:** algunos endpoints invocan controladores del núcleo `api/` (p. ej. `LocalController`,
> `InsumoController`, `VcsController`, `VentaController`). Se indican explícitamente como "core".

## Notas y supuestos (versión programable)

1. Nombres y cifras ("Carne QA", "Proveedor QA", "Plato QA") son datos de ejemplo para la matriz; el bot los creará en la ejecución real.

# Reporte Técnico — Reglas de Kardex para la Matriz E2E Masiva (Insumos / Consumibles / Productos)

> Fuente: PHP en `C:\xampp\htdocs\webapp` (`logistica/` + `api/`). Solo reglas, fórmulas y literales. Sin casos de prueba.

## 1. Aprovisionamiento Solicitud → OC → Compra

### 1.1 Entrada al Kardex por tipo de ítem

**Regla: el Kardex distingue por `presentacioninsumo_id / producto_id / presentacioncompraproducto_id`, no por `item_tipo`.** El mapeo es (`api/definitions.php:964-974`, `OrdencompraLogisticaController.php:1510-1514`):

- `item_tipo=1` = Insumo **y** Consumible/Activo/Descartable (subtipos 5/6 por `TIPOINSUMO_CONSUMIBLE/ACTIVO`); `item_tipo=2` = Producto de reventa.
- Ramas de entrada en compra (`api/entity/Detallecompra.php:129-169`, `DetallecompraLogistica.php:77-186`):
  - `_esUnaPresentacionInsumo()` → `Insumo::incrementarStockPorCompra(ENTRADA_COMPRA…)` (`:469-470`).
  - `_esUnProducto()` → `Producto::incrementarStockPorCompra(ENTRADA_COMPRA…)` (`:514-515`), con `producto_controlstock != SI ⇒ return` sin tocar Kardex (`Producto.php:2752-2766`).
  - `_esPresentacionCompraProducto()` → cantidad `× presentacioncompraproducto_cantidad`, costo `/ cantidad` (`:526-539`).

**Diferencia Consumible (la única estructural): tabla espejo.** Si `insumo.insumo_consumible='1'` (`InsumoLogistica.php:6202-6210 `esConsumible()`), el movimiento va a **`movimientoalmacenconsumible`** (`MovimientoalmacenconsumibleV2`, constantes invertidas `TIPO_PRODUCTO=1, TIPO_INSUMO=0` en `:25-27`) en vez de `movimientoalmaceninsumo` (`InsumoLogistica.php:6212-6237 registrarMovimientostock()`, `:6239-6274 actualizarMovimientostock()`; anulación `DetallecompraLogistica.php:735-754`). Consecuencia para el oráculo: el stock/costo de un consumible **no se lee** en `obtenerStockYCosto` ni en `movimientoalmaceninsumo`; hay que consultar la tabla espejo (y `Utility::existeMovimientosPosteriores` conmuta tabla por `item_subtipo==TIPOINSUMO_CONSUMIBLE`, `Utility.php:8086`).

### 1.2 Vínculos del canje

`requerimientocompra.ordencompra_id` + estado `REQUERIMIENTOCOMPRA_CANJEADO` + pivote `ordenrequerimientocompra`; `ordencompra.compra_id / guia_id` + estados `PENDIENTE/PROCESADA/ENPROCESO/ANULADA`; `compra.ordencompra_id` (FK) y `guia.ordencompra_id`. Al canjear: `$ordencompra->setCompra_id(…); setOrdencompra_estado(ORDENCOMPRA_PROCESADA)` (`CompraLogistica.php:1256-1260`; espejo en `GuiaLogistica.php:498-511`).

### 1.3 Literales de bloqueo (JSON `mensajes[]`)

Anular OC ya canjeada (`smart/validators/OrdencompraLogisticaValidator.php:93-127`):
- `:119` `"No se puede anular una orden canjeada por una compra."` (tiene `compra_id`)

Registrar OC desde solicitud (`:140-154`): `"El requerimiento con codigo $id ya tiene una orden de compra con codigo … vinculado."`, `"… ha sido anulado."`, `"… aun no ha sido aprobado."`, `"… ya ha sido canjeado."`, `"… ha sido agrupado."`, `"… no es valido."` Anular solicitud convertida: **sin bloqueo** (`RequerimientocompraLogisticaValidator.php:75-79` retorna vacío; el freno está del lado OC).

## 2. Anulaciones cruzadas y stock negativo

### Regla: el backend **ejecuta y permite el negativo (-5)**. No hay validador de saldo en la ruta de anulación.

Evidencia encadenada para el escenario 40 FL→SUC + merma 5 + anular traslado:

1. **Endpoint real**: `POST /anularMovimmiento` (doble `m`, `rest/movimiento/index.php:34,229-234`). El `GET /anularMovimiento/{id}/{devolverStock}` (`:22,152-156`) apunta a un método inexistente en el controlador (roto; no usar).
2. **Única guarda**: `mermaList = obtenerMermaVinculado()` = mermas con `merma.movimiento_id = movimiento_id` **y** `merma_estado=ACTIVO` (`MovimientoLogistica.php:136-142`). Una merma posterior independiente en Sucursal no vincula → no bloquea. Si vinculara: `"El movimiento esta vinculado a una salida de stock, para poder anular el movimiento primero anule la salida de stock cod: …"` (`MovimientoLogisticaController.php:1011-1083`, espejo en `:712`).
3. **Sin check de stock**: `MovimientoValidator::_validateAnular` tiene el chequeo de movimientos posteriores **desactivado con `false &&`** (`api/validators/MovimientoValidator.php:49-70`; el mensaje `"El movimiento tiene productos o insumos que ya han sido procesados."` es inalcanzable; en `_validateModificar:84` sí está activo). `movimientoTieneErrores()` (`MovimientoLogistica.php:1260-1286`) solo mira guías/requerimientos/cuadre/fecha, nunca saldo.
4. **Reversión lógica, no contra-movimiento**: `MovimientoLogistica::anular()` (`:360-383`) marca `movimiento_estado=INACTIVO` + `anularMovimientosPorMotivoYMotivoID(SALIDA/ENTRADA_MOVIMIENTO, id)` (ambas tablas, insumo y consumible) → cada kardex se marca `fueeliminado=SI` y se recalcula hacia adelante (`MovimientoalmaceninsumoV2.php:359-399,502-505,2182-2191`). Resultado del escenario: Sucursal `0 − 5 = -5` en `saldoactual`. (El motor viejo sí insertaba `SALIDA_ANULAR_MOVIMIENTO` — `api/entity/Movimiento.php:344-352` — pero V2 ya no.)
5. **El flag de negativo es opt-in y no aplica a anulaciones**: `operacionRestringidaPorStockNegativo=true` solo si `CONFIGURACION_RESTRINGIR_SALIDAS_SI_NO_HAY_STOCK` está activa por local (`MovimientoalmaceninsumoV2.php:3322-3341`; descripción en `ConfiguracionController.php:2324`), y `anular()` jamás lo consulta. Éxito: `"Se anulo con exito el movimiento."`; ya anulado: `"El movimiento esta anulado."`; inexistente: `"Error, no fue posible encontrar el movimiento que desea anular."`.

Mismo patrón al anular merma/salida (`MermaLogistica.php:130-155`, validator `:49-60`): solo antigüedad (`"La merma tiene más de X días registrada."`); el check de stock (`"La merma tiene productos o insumos sin stock."`, `:65-115`) está comentado y era solo de registro. Éxito: `"Merma Anulado con exito"` (sic, `:252`).

## 3. Matemática de ajustes: el costo se congela en salidas

### Regla: **ninguna SALIDA recalcula el PPP; solo debita cantidad con costo 0.** Solo las ENTRADAS (y el cuadre tipo `TIPO_CUADRE` con cantidad > 0) promedian.

- `Insumo::disminuirStock` (`api/entity/Insumo.php:424-425`) y `Producto` (`:2005-2006`) llaman `parser(…, cantidad, 0, motivo, …, DISMINUYE_STOCK)`; `Detallemerma` fija `detallemerma_costo = 0` (`:175,300`).
- `_registrarPonderado` rama `TIPO_SALIDA` (`MovimientoalmaceninsumoV2.php:208-213`, espejo `:329-334`, consumibles `:178-183`): `costooperacion=0, saldoactual=0, costopromedioactual=0`. Stock = `Σentradas − Σsalidas` (`:1143`).
- Fórmula PPP, **solo rama ENTRADA** (`:789,899-901`; preview `Insumo.php:1212-1215` con `round(…,8)`):
  `nuevoPPP = ((stockAnt × PPPant) + (costoOp × cantOp)) / (stockAnt + cantOp)`.

### Cuadre de stock (`CuadremanualLogistica.php`)

- **Sobrante** (aumento): entra a `costoNuevo` digitado, o `costo` de grilla, o PPP vigente (`obtenerCostoOperacion:532-556`) vía `ENTRADA_REGULAR_STOCK_MANUAL` + `TIPO_CUADRE` (`:594-602,964,1057-1058`); el motor fija `costopromedioactual = costooperacion` (`MovimientoalmaceninsumoV2.php:229-250`). Un sobrante **sí mueve el PPP** (entra como compra al costo declarado).
- **Faltante** (disminución, `:1384,1488-1628`): doble movimiento — (1) `SALIDA_MERMA_CUADRE_STOCK` por la diferencia (costo a 0, no toca PPP) + (2) `SALIDA_REGULAR_STOCK_MANUAL` de **cantidad 0** con `TIPO_CUADRE` que solo fija/revaloriza costo si `costo != costoNuevo` (si son iguales, no altera nada, `:702-704`). El costo queda en `detallecuadremanual_costopromedio` (`:1626`).
- Arqueo (`ArqueoinventarioLogistica.php:669,698,1079,1118`) solo lee y notifica; el ajuste real lo emite Cuadre. Sincronización DIAN/POS (`SincronizacionrecepcioncompraLogistica.php`) no toca stock/costo.
